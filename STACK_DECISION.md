# Вибір стеку

Цей документ пояснює, чому обраний саме цей стек, у розрізі пріоритетів з ТЗ.

## Підсумок

| Шар | Вибір |
|---|---|
| Backend | Laravel 11 (PHP 8.2) |
| Frontend | Vue 3 + Inertia.js |
| CSS | Tailwind CSS v4 |
| БД | MySQL |
| Cron/scheduler | вбудований Laravel Scheduler |
| Telegram | офіційний Bot API через webhook, тонкий HTTP-клієнт на `Http` facade |
| Auth | вбудований `Auth::attempt`, без Breeze/Fortify |
| Admin UI | звичайні Inertia-сторінки за `auth` middleware, без Filament/Nova |

## Чому саме так, за пріоритетами з ТЗ

**1. Швидкий реактивний інтерфейс.**
Inertia.js дає SPA-подібну навігацію (перемикання тижнів/років без повного
перезавантаження сторінки) без потреби піднімати окремий REST API та окремий
frontend-проєкт. Дані сторінки — це не JSON-ендпоінти, а звичайні
контролер-пропси; клієнт лишається одним Vue-додатком. Це прямо відповідає
вимозі ТЗ "якщо дані не realtime — server-driven UI достатньо, WebSocket не
потрібен": ми не використовуємо WebSocket, бо оновлення статистики відбувається
раз на дію (надіслав результат / раз на тиждень), а не щосекунди.

**2. Проста підтримка проєкту.**
Один Laravel-застосунок, один git-репозиторій, один `composer install && npm
install`, стандартна структура MVC + невеликий шар `app/Services`. Немає
мікросервісів, немає окремого API-сервера, немає Docker/Redis/черг — усе, що
не потрібно для першої робочої версії, свідомо не додано.

**3. Зручна робота з Telegram Bot API.**
Webhook-контролер + `Http`-клієнт Laravel замість важкого SDK: усього ~40
рядків для відправки повідомлень, легко тестувати через `Http::fake()`.
Секретний токен вебхука перевіряється окремим middleware
(`X-Telegram-Bot-Api-Secret-Token`).

**4. Надійна робота з MySQL.**
Eloquent ORM з міграціями, транзакціями та `lockForUpdate()` для атомарного
закриття тижня — саме те, що потрібно для коректної, не дублюючої обробки
cron-задачі.

**5. Проста настройка cron/scheduler.**
Один рядок у `routes/console.php`
(`Schedule::command('week:close')->weeklyOn(0, '00:00')->withoutOverlapping()->onOneServer()`)
і один системний cron-запис (`* * * * * php artisan schedule:run`). Ніяких
Redis/Horizon для цього не потрібно — `withoutOverlapping()`/`onOneServer()`
використовують `database`-кеш, який уже налаштований.

**6. Зручний деплой на звичайний VPS.**
Laravel деплоїться на будь-який хостинг з PHP-FPM (Apache/nginx) + MySQL —
без Docker. Див. [DEPLOYMENT.md](DEPLOYMENT.md).

**7. Хороша структура коду.**
Бізнес-логіка винесена із контролерів у прицільні сервіси
(`app/Services/{Weeks,Torcoins,Parsing,Stats,Telegram}`), кожен з чіткою
відповідальністю та unit-тестами. Контролери — тонкі, лише формують пропси
для Inertia.

**8. Мінімум зайвої складності.**
Свідомо НЕ додано: Docker, Redis, черги, WebSocket, окремий SPA/REST API,
важкі admin-пакети (Filament/Nova), Breeze/Fortify для аутентифікації (на 1
адмін-акаунт це зайве — вистачає `Auth::attempt` у 15-рядковому контролері).

## Альтернативи, які розглядались і чому відхилені

- **Next.js/Nuxt + окремий REST API** — дало б трохи кращий edge-рендеринг,
  але подвоїло б кількість деплой-юнітів (frontend + backend) і вимагало б
  проєктувати повноцінний REST/JSON API там, де Inertia вирішує це "з коробки"
  одним застосунком. Для клубного проєкту на одного розробника — зайва
  складність.
- **PostgreSQL замість MySQL** — обидва підходять; MySQL обраний як
  дефолтний і найпоширеніший варіант для звичайного shared/VPS-хостингу,
  який згадується в ТЗ.
- **Queue workers (Redis/Horizon) для відправки Telegram-повідомлень** —
  не потрібні: повідомлень мало (одне на дію учасника), синхронна відправка
  через `Http`-клієнт займає мілісекунди і не блокує UI сайту (бот і сайт —
  різні запити).
