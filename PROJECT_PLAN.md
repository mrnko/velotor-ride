# Архітектура проєкту

Короткий довідник по тому, як влаштований проєкт, для тих, хто підключається
до підтримки чи розвитку.

## Огляд

Velotor Ride — Telegram-бот + сайт статистики велоклубу. Учасники надсилають
кілометраж у Telegram-чат, бот зберігає результат і рахує рейтинги; сайт
показує поточний тиждень, архів, річні рейтинги та профілі учасників.
Детальніше про вибір стеку — [STACK_DECISION.md](STACK_DECISION.md).

## Модель даних

- **`participants`** — учасник клубу, ключ — `telegram_user_id` (унікальний).
- **`weekly_periods`** — тиждень клубу: `year`, `week_number`, `start_date`,
  `end_date` (дати визначають межі, а не самé число тижня), `status`
  (`active`/`closed`), `total_distance`, `report_sent_at`, `closed_at`.
  Унікальність по парі `(year, week_number)`.
- **`ride_results`** — один запис результату, завжди прив'язаний до
  `weekly_period_id` (FK) — саме це структурно виключає клас багів "стик
  року", що був у legacy-проєкті (там фільтрація йшла лише по голому номеру
  тижня, без року).
- **`bot_reports`** — лог надісланих тижневих звітів (для ідемпотентності
  та історії).
- **`settings`** — key/value налаштування, які можна міняти з адмінки без
  редеплою (chat id, timezone, ліміти валідації).
- **`bot_message_logs`** — лог кожного вхідного Telegram-update (для
  діагностики через адмінку).

## Сервісний шар (`app/Services`)

- **`Weeks\WeekResolverService`** — вся логіка "який зараз тиждень" за
  діапазоном дат (тиждень: понеділок 00:00 → наступний понеділок 00:00, часовий
  пояс з `config('velotor.timezone')`), обчислення наступного вікна з
  правильним переходом через Новий рік.
- **`Weeks\WeeklyCloseAction`** — ідемпотентне закриття тижня: транзакція +
  `lockForUpdate()`, перевірка `report_sent_at`, і додатковий guard "тиждень
  ще не закінчився" (щоб повторний виклик scheduler відразу після закриття
  не закрив і щойно відкритий наступний тиждень). Один код-шлях і для cron
  (`week:close`), і для кнопки в адмінці (`force: true`).
- **`Parsing\ResultParser`** — розпізнавання "результат 10 км" / "+10 км"
  тощо, з валідацією діапазону (`ParsedResult` — matched/valid/invalidReason).
- **`Stats\DuplicateGuard`** — захист від випадкового дубля результату.
- **`Stats\StatsRecalculationService`** — перерахунок `total_distance` з
  `ride_results` (використовується адмінкою після ручного редагування).
- **`Stats\LeaderboardService`** — єдине місце, де рахуються рейтинги
  (тиждень/рік/усі часи) і зведена статистика учасника; використовується і
  ботом (`/me`, `/top`, ...), і сайтом — без дублювання SQL.
- **`Torcoins\TorcoinCalculator`** — `floor(km / 100)`.
- **`Telegram\*`** — `TelegramClient` (тонкий HTTP-клієнт), `UpdateHandler`
  (оркестрація одного вхідного update), `BotCommandRouter` +
  `Commands\*Command` (один клас на команду бота).

## Маршрути

Публічний сайт (`routes/web.php`) — усе через Inertia, без окремого REST API:
`/`, `/week`, `/weeks/{year?}`, `/weeks/{year}/{weekNumber}`, `/year/{year?}`,
`/all-time`, `/participants/{participant}`, `/rules`.

Telegram-вебхук: `POST /telegram/webhook` (захищений
`X-Telegram-Bot-Api-Secret-Token`, поза CSRF).

Адмінка: `GET/POST /admin/login`, далі `/admin/*` за `auth` middleware —
dashboard, учасники, результати (перегляд/редагування/видалення), тижні
(перегляд + ручне закриття), логи бота, налаштування.

## Що можна покращити далі

- Пагінація/віртуалізація для дуже великих таблиць рейтингу (зараз клієнтський
  пошук/сортування розраховані на клуб у десятки-сотні учасників).
- Ролі в адмінці (зараз усі автентифіковані користувачі — повноцінні адміни).
- SSR для Inertia, якщо знадобиться SEO для публічних сторінок.
